# Daily goal: P1

## Context

P1 is the only phase of the daily-goal feature (see `PLAN.md`). It replaces the fixed `GOAL_ML = 2000` in `src/main.ts` with a goal the user sets using a −/+ stepper (500–5000 ml in steps of 250, default 2000, not stored). It also adds a thick progress bar with the "X / Y ml (N%)" text drawn inside it, and a green "goal reached" state with a "✓ Goal reached" pill badge. When P1 is done the user can try all of it in the review build.

The user's visual picks in `PLAN.md` → Decisions are fixed. Page order: heading, goal stepper row, bar (text inside), badge (only when reached), "+ glass" button. The "N%" is the real, uncapped percentage, and the bar width stays capped at 100%. Where this file is more specific than `PLAN.md` → Architecture (markup structure, exact colors), this file wins. The rulings at the end explain each difference.

## Step 1: Goal logic and tests (`src/water.ts`)

Keep `GLASS_ML`, `total()` and `progress()` unchanged. `progress()` stays capped at 1 and drives the bar width.

Add to `src/water.ts`:
```ts
export const GOAL_DEFAULT_ML = 2000
export const GOAL_MIN_ML = 500
export const GOAL_MAX_ML = 5000
export const GOAL_STEP_ML = GLASS_ML // 250

/** Goal after one stepper press, clamped to [GOAL_MIN_ML, GOAL_MAX_ML]. */
export function stepGoal(goalMl: number, direction: 1 | -1): number
// Math.min(GOAL_MAX_ML, Math.max(GOAL_MIN_ML, goalMl + direction * GOAL_STEP_ML))

/** True once the day's total meets or passes the goal. */
export function goalReached(glasses: number, goalMl: number): boolean
// total(glasses) >= goalMl

/** Real, uncapped percentage of the goal, rounded to a whole number (e.g. 125). */
export function percentOfGoal(glasses: number, goalMl: number): number
// Math.round((total(glasses) / goalMl) * 100)

/** The text inside the bar: "1500 / 2000 ml (75%)". */
export function summaryText(glasses: number, goalMl: number): string
```

Total and goal are both multiples of 250 and the goal is at most 5000 ml (20 glasses). Below the goal the ratio is therefore at most 19/20 = 95%, so the rounded percentage can never read "100%" while the goal is not yet reached. No special case is needed.

Tests in `src/water.test.ts`. Keep the two existing tests and add:
- `stepGoal`: 2000 → 2250 (+1) and 2000 → 1750 (−1). At the bounds: 500 with −1 stays 500, 5000 with +1 stays 5000, 750 with −1 gives 500, 4750 with +1 gives 5000.
- `goalReached`: 7 glasses with goal 2000 is false (1750), 8 is true (exactly 2000), 10 is true (2500). With a custom goal, 2 glasses with goal 500 is true.
- `percentOfGoal`: 6 glasses with goal 2000 gives 75, 10 glasses with goal 2000 gives 125 (uncapped), 0 glasses gives 0, 1 glass with goal 3000 gives 8 (rounded from 8.33).
- `progress`: stays at 1 for a custom goal (e.g. 10 glasses with goal 1500).
- `summaryText`: 6 glasses with goal 2000 gives `"1500 / 2000 ml (75%)"`. 10 glasses with goal 2000 gives `"2500 / 2000 ml (125%)"`.
- Constants: `GOAL_STEP_ML === GLASS_ML`, and the default 2000 lies inside [500, 5000].

## Step 2: Mount once, update in place (`src/main.ts`)

Replace the `GOAL_ML` constant and the `innerHTML`-on-every-click `render()` with:

- State: `let glasses = 0` and `let goalMl = GOAL_DEFAULT_ML`. Neither is stored.
- `mount()` runs once. It writes the markup below into `#app`, looks up the elements it needs once (they are kept in module-level `const`s, or in one `els` object), and attaches the three click listeners. It ends by calling `update()`.
- `update()` changes no markup. It sets:
  - `#goal-value` textContent to `` `${goalMl} ml` ``.
  - `#goal-dec`'s `aria-disabled` to `"true"` when `goalMl <= GOAL_MIN_ML`, else `"false"`, and the same for `#goal-inc` with `goalMl >= GOAL_MAX_ML`.
  - `#bar-fill`'s `style.width` to `` `${progress(glasses, goalMl) * 100}%` ``.
  - `#bar`'s `aria-valuenow` to `Math.round(progress(glasses, goalMl) * 100)`.
  - `#summary` textContent to `summaryText(glasses, goalMl)`.
  - Reached state: `const reached = goalReached(glasses, goalMl)`, then `bar.classList.toggle('is-reached', reached)` and `goalBadge.hidden = !reached`.
- Handlers. `#add`: `glasses++` then `update()`. `#goal-dec`: `goalMl = stepGoal(goalMl, -1)` then `update()`. `#goal-inc`: `goalMl = stepGoal(goalMl, 1)` then `update()`. `stepGoal` already clamps, so a click on an `aria-disabled` button changes nothing, and the handlers don't need their own guard.

Markup that `mount()` writes (every button gets `type="button"`):
```html
<h1>Water</h1>
<div class="goal-row">
  <span class="goal-label">Goal</span>
  <button type="button" id="goal-dec" class="step-btn" aria-label="Decrease goal">−</button>
  <span id="goal-value" class="goal-value" aria-live="polite">2000 ml</span>
  <button type="button" id="goal-inc" class="step-btn" aria-label="Increase goal">+</button>
</div>
<div class="bar-wrap">
  <div id="bar" class="bar" role="progressbar" aria-label="Daily goal progress"
       aria-valuemin="0" aria-valuemax="100" aria-valuenow="0">
    <div id="bar-fill" class="bar-fill"></div>
  </div>
  <p id="summary" class="bar-text"></p>
</div>
<div id="goal-status" role="status">
  <span id="goal-reached" class="badge" hidden><span aria-hidden="true">✓</span> Goal reached</span>
</div>
<button type="button" id="add">+ glass</button>
```
The − label is U+2212 (MINUS SIGN), matching the mockup. Copy is exactly "Goal", "2000 ml", "✓ Goal reached" and "+ glass".

`#summary` is a sibling of `#bar` that CSS lays over it, not a child. ARIA treats the children of a `progressbar` as presentational, so text placed inside it would be lost to screen readers. As a sibling it stays a normal paragraph that screen readers read in full, uncapped percentage included.

No unit tests in this step. There is no DOM library and adding jsdom would add a dependency (PLAN ruling). Step 2 is checked in the browser (see Verification).

## Step 3: Styles (`index.html`)

Add one `<style>` block in `<head>`. The colors come from the mockup the user picked from (https://claude.ai/artifact/Q5L13xfYr5ZpHvSwbSHqzE). Two text colors are darkened for contrast; see the rulings.

- **Page shell (Default, pending decision):** `body { margin: 0; padding: 24px 16px; font: 16px/1.4 system-ui, -apple-system, sans-serif; color: #16232c; }`, and `#app { max-width: 360px; margin: 0 auto; display: grid; gap: 12px; }` with `h1 { margin: 0 }`. This matches the mockup's phone card, minus the card border, and keeps the 34px bar from stretching across a wide desktop window.
- **Stepper row:** `.goal-row { display: flex; align-items: center; gap: 8px; font-variant-numeric: tabular-nums; }`. `.goal-label` uses muted `#5d6d78` at 0.9rem with `margin-right: 4px`. `.goal-value` is `font-weight: 600` with `min-width: 4.5em; text-align: center`, so the buttons don't shift between "500 ml" and "5000 ml". `.step-btn` is 30×30px, `border-radius: 8px`, `border: 1px solid #d6e0e6`, `background: #f3f6f8`, `font: inherit; font-size: 1rem; line-height: 1`. `.step-btn[aria-disabled="true"]` gets `opacity: .4; cursor: not-allowed`.
- **Bar:** `.bar-wrap { position: relative; }`. `.bar` is 34px tall, `border-radius: 10px`, `background: #dde8f1` (track), `overflow: hidden`. `.bar-fill` is `height: 100%`, `width: 0`, `border-radius: 10px`, `background: #2b7fd4`, `transition: width 200ms ease-out, background-color 200ms ease-out`. `.bar.is-reached .bar-fill { background: #2f9e5b; }`.
- **Text inside the bar:** `.bar-text { position: absolute; inset: 0; margin: 0; display: flex; align-items: center; padding-inline: 12px; font-size: .85rem; font-weight: 600; color: #0a1116; font-variant-numeric: tabular-nums; pointer-events: none; }`. Left-aligned, as picked.
- **Badge:** `.badge { display: inline-block; justify-self: start; background: #e3f4ea; color: #1f7a43; font-weight: 600; font-size: .85rem; padding: 3px 10px; border-radius: 999px; }`. `#goal-status { margin-top: -12px; }` together with `.badge { margin-top: 12px; }`. While the badge is hidden the empty status div adds no extra gap, so "+ glass" sits 12px under the bar. When the badge shows, it sits 12px under the bar and 12px above "+ glass". `#goal-status` is never hidden itself, so the live region stays in place.
- **"+ glass" button:** `justify-self: start` so it doesn't stretch across the grid. Otherwise it keeps the browser default look.
- **Reduced motion:** `@media (prefers-reduced-motion: reduce) { .bar-fill { transition: none; } }`.
- Light colors only. The app has no dark mode today, and this phase doesn't add one.

## Verification

**Automated:** `src/water.test.ts` (Step 1 cases), then the Pipeline verify command `npm test && npm run build`. `tsc --noEmit` in the build also catches unused imports left over from `GOAL_ML`.

**Browser checks** (review build: `npm run build && npm run preview`, open the printed URL):
1. On load, the order is heading, the "Goal − 2000 ml +" row, the bar with "0 / 2000 ml (0%)" inside and an empty track, then "+ glass". No badge shows.
2. Click "+ glass" 6 times. The text reads "1500 / 2000 ml (75%)", the blue fill covers about 3/4 of the bar, and the text stays readable over both the fill and the track.
3. Click "+ glass" 2 more times (2000 ml). The fill turns green and is full, the text reads "2000 / 2000 ml (100%)", and the "✓ Goal reached" pill appears under the bar.
4. Click "+ glass" 2 more times. The text reads "2500 / 2000 ml (125%)" and the bar stays full and green.
5. Click + until 5000. The text and bar update on each click. At "5000 ml" the + button looks disabled and further clicks change nothing. The badge disappears as soon as the goal passes the total (at 2750) and the fill turns blue again.
6. Click − down to 500. − looks disabled at 500, and the badge and green fill come back once the goal is ≤ 2500.
7. Keyboard: Tab to + and press Enter or Space repeatedly up to 5000. Focus stays on the button the whole time, including at the bound. Tab order: −, +, "+ glass".
8. Reload. The goal is back to 2000 and the glasses are back to 0.
9. Accessibility tree (DevTools → Accessibility): `#bar` is a progressbar named "Daily goal progress" with a value of 0–100. `#summary` text is exposed. The stepper buttons are named "Decrease goal" and "Increase goal" and report disabled at the bounds.
10. Narrow window (about 320px wide): nothing scrolls sideways, the stepper row stays on one line, and "5000 / 5000 ml (100%)" fits inside the bar.
11. With reduced motion emulated (DevTools → Rendering), the fill jumps with no animation.

**Device checks:** none (PLAN: a desktop browser check plus the narrow-window check cover it).

## Rulings made in this phase plan

- Ruling: `#summary` is an overlaid sibling of `#bar`, not a child — progressbar children are presentational in ARIA, so text inside it would be hidden from screen readers — cost if wrong: low, a markup move.
- Ruling: stepper bounds use `aria-disabled="true"` rather than the `disabled` attribute — a button that becomes `disabled` drops keyboard focus to `<body>` at the bound; `stepGoal` clamps, so clicks still do nothing — cost if wrong: low.
- Ruling: colors come from the mockup the user picked from (`#2b7fd4` fill, `#2f9e5b` reached, `#dde8f1` track), not PLAN's `#2b7de9`/`#2e9d5b` — that is what the user saw, and the difference is barely visible — cost if wrong: two hex values.
- Ruling: the text inside the bar is `#0a1116` (the mockup used `#16232c`) and the badge text is `#1f7a43` (the mockup used `#2f9e5b`) — the mockup values measure about 3.9:1 on the blue fill and 3.0:1 on the badge, below WCAG AA 4.5:1 for 13.6px text; the new values reach about 4.6:1 and 4.7:1 and look almost the same — cost if wrong: two hex values.
- Ruling: `summaryText()` and `percentOfGoal()` live in `water.ts` — this makes the uncapped percentage (pick 4) unit-testable without a DOM — cost if wrong: none.
- Ruling: the badge sits in an always-present `role="status"` container — this way, reaching the goal is announced to screen readers — cost if wrong: low.
- Ruling: the empty status container is cancelled out with a −12px margin (the badge carries +12px) — this avoids a double gap when nothing is reached, without hiding the live region (`display: none`/`contents` can drop it from the accessibility tree) — cost if wrong: low.
- Ruling: no dark mode — the app has none today — cost if wrong: one extra media block later.
